# ADR-001: 모듈러 모놀리스로 시작한다

- 상태: 채택됨
- 날짜: 2026-08-24

## 배경

StopBell에는 모바일 API, 알림 생명주기 관리, 교통 데이터 제공자 연동, 주기적 모니터링, 영속성 관리, 푸시 알림이 필요하다.

이 관심사는 이론적으로 여러 개의 배포 가능한 서비스로 분리할 수 있다. 그러나 V1에서는 독립적인 확장이나 배포가 필요하다는 근거가 없다.

## 검토한 선택지

### 선택지 A — 논리적 모듈로 구성한 단일 Spring Boot 애플리케이션

장점:

- 단순한 로컬 개발
- 단순한 디버깅
- 단순한 배포
- 직관적인 트랜잭션 처리
- 낮은 운영 부담
- 요구사항이 변하는 동안 쉬운 리팩터링

단점:

- 컴포넌트를 독립적으로 확장할 수 없음
- 부주의한 패키지 경계는 결합도를 높일 수 있음

### 선택지 B — 처음부터 마이크로서비스

장점:

- 이론상 독립적인 배포/확장 가능
- 명시적인 네트워크 경계

단점:

- 서비스 디스커버리와 네트워크 장애에 대한 고려 필요
- 더 많은 배포/설정 작업
- 분산 트랜잭션과 상태 관리의 복잡성
- V1에 필요하다는 검증된 근거 없음

## 결정

V1에서는 하나의 Spring Boot 백엔드를 배포하고, 이를 alarm, transit, notification, user와 같은 명확한 논리적 모듈로 구성한다.

## 근거

V1의 주요 위험은 백엔드가 Domain별로 독립 확장할 수 있는지 여부가 아니라, StopBell이 실제 교통 이벤트를 신뢰할 수 있게 감지하고 휴대폰에 알림을 보낼 수 있는지 여부이다.

모듈러 모놀리스는 코드에서 Domain 경계를 표현하면서 인프라 운영 부담을 최소화한다.

## 결과

- 백엔드 기능은 하나의 Spring Boot 애플리케이션에 둔다.
- 패키지 설계에서는 모듈 경계를 계속 지켜야 한다.
- 내부적으로 서비스 간 메시징이나 네트워크 API는 필요하지 않다.
- 측정을 통해 필요성이 확인되면 이후 분리할 수 있다.

## 재검토 시점

다음 중 하나 이상이 사실이 되면 이 결정을 재검토한다.

- 특정 워크로드가 독립적으로 확장되어야 하며, 이것이 비용이나 신뢰성에 실질적인 영향을 줌
- 컴포넌트별 배포 빈도가 크게 다름
- 팀 소유권에 따라 강한 서비스 경계가 필요함
- 하나의 백엔드 프로세스가 더 단순한 방법으로 해결할 수 없는 운영 병목이 됨
