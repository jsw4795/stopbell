# ADR-011: 탑승 차량 추천과 사용자 차량번호 확인

- 상태: 채택됨
- 날짜: 2026-10-19
- 대상: TASK-902 설계. Backend/Flutter 구현과 DB Schema 변경은 포함하지 않음

## 배경

[TASK-901 조사](../research/TASK-901-bus-vehicle-identification.md)는 TAGO `vehicleno`, 서울 `vehId/plainNo`와 제한된 정상 진행 관측을 확인했다. GPS 없는 API는 사용자 본인이 어느 버스 안에 있는지 관측하지 않으며, 차량 ID의 장기 안정성·회차·소실 후 동일성과 실제 차체/차내 번호 대응은 검증되지 않았다. 조사 완료를 제품 정확성 검증 완료로 취급하지 않는다.

개발자는 TASK-902 검토 후 다음을 확정했다.

- 승차 정류장과의 간격은 화면 정렬 보조 정보이며 실제 탑승 가능성·신뢰도의 직접 근거가 아니다
- 정상 호출한 Provider 응답은 해당 조회 시점의 최신 가용 데이터로 사용한다. TAGO 원본 생성시각 부재만으로 추천을 보류하지 않으며, 조회 시각과 실제 물리적 위치의 일치를 보장하지 않는다
- 사용자가 실제 차량번호를 직접 대조하고 확정하는 방식을 핵심 UX로 채택한다

사용자 보장 동작은 [요구사항](../requirements.md#phase-9-탑승-차량-추천과-확인), Domain 불변 조건은 [Domain Model](../domain-model.md#탑승-차량-추천과-확인), 실행 경계는 [Architecture](../architecture.md#transit)가 소유한다. 이 ADR은 추천 알고리즘·예시·대안과 후속 구현 제약을 기록한다. 세션 Entity/상태 enum, API field·동시성·만료 및 Persistence 계약은 TASK-903에 남긴다.

## 검토한 선택지

### 선택지 A — 정류장 근접도와 버튼 시각으로 탑승 확률을 계산

- 장점: 사용자가 번호를 확인하기 전 한 차량을 쉽게 강조 가능
- 단점: 사용자 실제 위치·승차 시각, Provider 지연, 밀집 차량·회차를 구별할 근거가 없어 점수와 확률을 정당화할 수 없음
- 판단: 채택하지 않음. 근접도·단일 후보·버튼 시각을 탑승 증거로 승격하지 않음

### 선택지 B — 원본 생성시각이 없는 Provider는 추천에서 제외

- 장점: 원본 age를 확인하지 못하는 한계를 보수적으로 처리 가능
- 단점: 정상 조회한 최신 가용 정보와 원본 age 보장을 혼동하며, TAGO의 번호 확인 후보까지 차단
- 판단: 채택하지 않음. 원본 시각 부재와 실제 식별·진행·응답 오류를 구분

### 선택지 C — 번호 대조 중심의 확인 후보와 보조 정렬

- 장점: Provider별 식별 정보를 보존하고 사용자가 이해할 수 있는 근거로 직접 확인 가능
- 단점: 번호를 읽을 수 없거나 대응이 불명확하면 미확정 유지. 번호 오확인을 시스템이 자동 검출할 수 없으며 정확한 물리 위치·동일 운행을 보장하지 못함
- 판단: 채택. 추천은 확인할 후보를 제시하는 의미이며 자동 확정이나 탑승 확률 추정이 아님

## 결정

### 1. 입력과 사용 범위

| 입력 | 사용 규칙 |
| --- | --- |
| 선택 Route | 필수. 내부 Route에서 provider/externalRouteId와 typed request context를 조회. 노선번호만으로 합치지 않음 |
| 하차 occurrence | 필수. 선택 Route와 목적 occurrence의 일관성 확인용이며 탑승 차량 식별 근거가 아님 |
| 승차 occurrence | 선택. 간격 정렬을 사용하려면 필요하며 같은 이름도 occurrence와 인접 이름으로 구별. 미입력이어도 번호 확인 경로 사용 가능 |
| 버튼 접수 시각 | 서버 Clock 기준 조회 문맥. 실제 승차 시각·사용자 위치·차량 통과 시각으로 대체하지 않음 |
| 사용자가 직접 확인한 전체 차량번호 | 선택 입력. 일치 후보를 먼저 찾는 용도. 사전 입력 없이 목록 번호를 실제 차량과 대조하는 경로도 지원 |
| 차량별 식별·진행·제공/수신 시각 | Provider별 검증과 근거 표시. 없는 값을 합성하지 않음 |

단말 GPS·위치 권한과 Provider GPS 좌표는 입력·정렬·식별·보류 해소에 사용하지 않는다. `destinationName`은 검증된 표시 metadata일 뿐 실시간 운행 방향이 아니며, `sectOrd == stOrd`, `nextStId`와 특정 occurrence의 동치 관계를 만들지 않는다. TAGO Arrival에는 차량 ID가 없으므로 선택 차량의 도착 근거로 연결하지 않는다.

### 2. 최신 가용 데이터와 시간

정상 호출은 HTTP 성공만을 의미하지 않는다. Provider 성공 코드·필수 envelope 및 현재 Client가 수행하는 완전성 검증을 통과한 응답이어야 한다. 그 응답은 조회 시점의 최신 가용 데이터로 받아들이되 개별 item의 식별 충돌·진행 모순 등은 별도로 검증한다.

TAGO `providerDataTime` 부재는 오류나 stale의 증거가 아니며 추천 차단 사유로 삼지 않는다. UI는 조회/수신 시각과, 제공시각이 있으면 그 시각을 구분한다. TAGO는 조회 시각을 보여 주면서 원본 갱신시각을 알 수 없고 실제 위치가 지연될 수 있다는 한계를 안내한다. 이를 이유로 정상 후보 전체를 보류 상태로 만들지 않는다. 서울 `dataTm`도 실제 물리 도착 시각의 보장은 아니다.

Polling 간격은 다음 외부 조회를 언제 실행할지, Observation Freshness는 확보한 관측을 언제까지 평가에 사용할지를 정한다. 둘을 같은 값으로 취급하지 않는다. 기존 fixed-delay 기본 `PT20S`, 기존 Observation Freshness 60초와 future/stale 판정, timeout·retry 설정은 변경하지 않는다. Freshness의 상세 계약은 [Domain Model](../domain-model.md#tracking-lifecycle)을 따른다. 성공 응답이라는 이유로 명시적으로 stale하거나 모순된 시각을 무시하지 않으며, 원본 시각이 없다고 임의 생성하지도 않는다.

과거 응답을 다시 표시하는 행위는 새 성공 조회가 아니다. 캐시·재표시로 `observedAt`을 새로 찍어 age를 초기화하지 않는다. 반대로 정상 재조회에서 같은 번호·진행이 반복됐다는 사실만으로 stale·정차·운행 종료를 단정하지 않는다. 버튼 전후 N초 또는 N정거장 이내를 탑승 판정 기준으로 추가하지 않는다. 추천 전용 TTL을 새로 도입하지 않으며 후보 화면/확정 요청의 별도 유효기간은 TASK-903에서 정한다.

### 3. 후보 생성·제외·보류

1. 선택 Route와 목적/선택적 승차 occurrence의 소속·metadata 존재를 검증한다. 없어지거나 의미가 바뀐 occurrence를 이름으로 자동 치환하지 않는다.
2. 해당 Route의 최신 가용 목록을 조회한다. TAGO cityCode는 요청 문맥으로만 유지하고 차량 키의 영구 identity로 승격하지 않는다.
3. Provider/Route 안에서 식별자와 사용자 표시 번호를 검증한다. 다른 Route·Provider의 같은 문자열을 합치지 않는다.
4. 식별 가능한 item은 위치 근거가 없어도 번호 확인 후보로 남긴다. 식별 불가·번호 충돌 item은 별도 불확실 항목으로 보존하고 후보 수에서 조용히 제거해 거짓 단일 후보를 만들지 않는다.
5. 검증 가능한 진행 근거만 부가 표시하고 §4의 순서로 보여 준다. 식별·진행 충돌을 정렬이나 번호 일치로 덮지 않는다.

| 상황 | 처리 |
| --- | --- |
| 정상 empty | 현재 조회 후보 없음. 운행 없음·미탑승·운행 종료를 단정하지 않음 |
| Provider/HTTP/transport/protocol 실패 또는 목록 불완전 | 추천 보류. 실패를 정상 empty로 변환하지 않음 |
| tracking ID 없음 | 해당 item은 확정 불가. 표시 번호로 ID를 합성하지 않음 |
| 서울 plainNo 없음 | 실제 번호 대조가 불가능하므로 해당 item의 사용자 확정 보류 |
| 동일 ID의 상이한 번호·진행, 동일 번호의 복수 ID | 관련 후보의 추천·확정 보류. 한쪽 ID나 번호를 임의 우선하지 않음 |
| 위치 ID/order 없음 | 번호 확인 후보 유지. 검증 불가 위치 근거만 사용하지 않음 |
| 진행 역행·ID/order 충돌·회차/분기/lap 모호성 | 위치 근거 사용 보류. 동일 차량·목적 traversal을 신뢰할 수 없으면 확정/추적 시작도 보류 |
| 승차 위치보다 앞/뒤에 관측 | 그 사실만으로 제외하지 않음. 지연된 버튼 조작·Provider 위치 지연 가능성을 추측으로 해소하지 않음 |
| 목적지 이후 관측 | 현재 참고 사실로 표시. 다음 lap을 자동 가정하거나 목적지를 자동 변경하지 않음. 추적 시작 가능 여부는 TASK-903 계약에 따름 |

일부 항목이 미검증이면 유효한 다른 후보를 보여 줄 수 있지만 전체 후보 중 유일성·최상위 탑승 가능성을 주장하지 않는다. 사용자가 번호를 대조했다는 사실도 충돌·진행 모순을 해결하는 대체 검증이 아니다.

### 4. 추천과 화면 정렬 알고리즘

추천 결과는 차량별 확인 정보와 그 근거를 갖는 목록이다. 가중치 점수·탑승 확률·신뢰도 수치·자동 선택을 제공하지 않는다.

1. 사용자가 전체 번호를 입력했다면 충돌 없이 정확히 일치하는 후보를 먼저 표시하고 `번호 일치` 이유를 제공한다. 일치 항목이 없으면 그 사실을 안내하고 다른 번호를 일치한 것처럼 대체하지 않는다.
2. 그 외 후보는 같은 확인 후보로 취급한다. 승차 occurrence와 진행 occurrence를 비교할 수 있는 항목은 metadata 배열의 index 차이 절댓값으로 보조 정렬한다. GPS 거리나 raw order 숫자 차는 사용하지 않는다.
3. 비교 가능한 항목은 간격 오름차순, 간격 미확인 항목은 별도 위치 미확인 구역에 표시한다. 위치 미확인이라는 이유로 실제 탑승 가능성이 낮다고 표시하지 않는다.
4. 같은 번호 일치 여부·같은 간격 또는 간격을 비교할 수 없는 후보 사이에는 추천 우열이 없다. 화면의 재현 가능한 순서는 전체 표시 번호, 이어서 opaque 내부 후보 reference 순으로 유지할 수 있으나 그 순서를 추천 근거로 노출하지 않는다. 구체 reference 형식은 TASK-903에서 정한다.

간격은 앞에 보여 줄 순서만 결정하며 후보 자격·확정 가능 여부·신뢰도·추천 배지·자동 확정에 영향을 주지 않는다. 가장 가까운 후보, 정확히 승차 occurrence에 대응한 후보, 후보 수가 한 대라는 조건 모두 실제 탑승의 증거가 아니다. 동률은 공동 후보로 남기며 제공시각 몇 초 차이로 해소하지 않는다.

서울의 exact `stId/stOrd + stopFlag=1`은 검증된 경우 해당 occurrence 도착 관측으로 표시할 수 있지만 사용자 탑승 사실은 아니다. TAGO ID/order 일치는 노선 진행 참고이며 직접 정차 flag가 아니다. 이 차이를 번호 대조가 필요 없는 확정 근거 또는 별도 탑승 신뢰도 단계로 만들지 않는다.

### 5. nodeid 없는 미정차·경유 가능 지점

`nodeid` 누락은 후보 제거 조건도, 미정차·경유 지점이라는 확인 사실도 아니다. TAGO 번호가 유효하면 번호 확인 후보로 보존한다.

order 단독 활용은 같은 Route의 metadata에 해당 양의 순번이 유일하게 존재하고, 그 Route의 realtime order 체계와 metadata 대응에 검증 근거가 있으며, 사용 가능한 동일 차량 관측과 모순되지 않고 회차·분기·lap이 모호하지 않을 때만 가능하다. 단지 metadata에 같은 숫자가 있다는 조건으로 검증됐다고 보지 않는다.

위 조건을 충족하면 진행 순서 참고와 보조 정렬에 활용할 수 있다. 누락 ID를 채우거나 metadata Stop 이름을 정확한 현재 정차 위치로 확정하지 않으며, 도착 또는 실제 탑승의 근거로 승격하지 않는다. 조건을 충족하지 못하면 번호 확인 후보와 위치 미확인 표시를 유지한다. current metadata 자체에 없는 경유 지점을 표현하려고 가짜 BusStop/occurrence나 Schema를 추가하지 않는다.

TASK-901 §17은 문제 item의 개별 order·차량별 연속 관측을 확보하지 못했다. 따라서 그 실측을 order 단독 활용의 검증 성공으로 사용하지 않는다.

### 6. 사용자 확인과 재조회

기본 흐름은 `탑승했어요 → 확인할 차량 목록 → 실제 전체 차량번호 대조 → 사용자 명시적 확정`이다. 사전 번호 입력은 필수가 아니며, 끝 네 자리는 검색 보조로만 사용할 수 있고 유일성·확정 근거가 아니다.

표시 정보는 전체 차량번호, 노선 구분 정보, 검증된 범위의 최근 진행/위치 설명, 조회 시각·선택적 제공시각, 번호 일치 이유, 미확인·실패 사유다. raw Provider ID나 임의 확률을 사람이 확인할 차량번호 대신 사용하지 않는다. 번호를 볼 수 없거나 기억이 불확실하면 미확정 상태로 남길 수 있어야 한다.

재조회는 후보 목록과 정렬만 갱신한다. 화면 선택을 자동 확정하거나 새 1순위로 옮기지 않는다. 확정 직전에는 대상 ID·표시 번호 대응과 유효성을 다시 검증하고, 후보 소실·변경·충돌이면 다시 확인하게 한다. 조회 순위·목록 index·표시 번호만으로 확정 대상을 식별하지 않는다. API·동시성·재확인·만료의 구체 계약은 TASK-903에서 정한다.

확정 뒤에는 추천 순위·가까운 차량·동일 번호의 다른 ID로 자동 변경하지 않는다. 소실·ID 변경·진행 모순·회차·식별 연속성 상실은 추적 판단 보류와 사용자 재확인 또는 종료로 복구한다. 같은 문자열이 재등장해도 동일 물리 차량·같은 운행으로 자동 복구하지 않는다. 재시작·일시 실패·소실 구분과 재개 조건도 TASK-903의 책임이다.

현재 [TAGO Client](../../backend/src/main/java/com/stopbell/transit/client/TagoVehicleLocationClient.java)는 `pageNo=1`, `numOfRows=1000`을 요청하고 `totalCount`가 null·음수이거나 실제 item 수와 다르면 `PROTOCOL` 실패다. 추가 페이지를 수집하는 구현은 아니다. 1,000건 초과 또는 Provider truncation 등으로 개수가 다르면 기존 실패 경로를 유지한다. 개수 일치는 item ID/order·중복·원본 age 및 물리 운행 집합의 완전성을 보장하지 않는다. 응답 pageNo/numOfRows를 별도로 검증하는 코드가 있다고 주장하지 않는다.

현재 [서울 detail Client](../../backend/src/main/java/com/stopbell/transit/client/SeoulBusVehicleDetailClient.java)는 요청/응답 vehId 일치를 검증하지 않고, [서울 Mapper](../../backend/src/main/java/com/stopbell/transit/mapper/SeoulBusTransitObservationMapper.java)는 plainNo를 TransitObservation에 보존하지 않는다. 후보 제공·확정에는 요청 ID 일치, roster/detail 번호 대응, 검증 가능한 metadata·시각의 보존이 필요하며 TASK-904/905의 최소 구현에 남긴다. detail에 현재 Route를 독립적으로 증명하는 필드가 없으므로 mapper가 요청 Route를 붙인 것을 현재 노선 소속의 독립 증명으로 사용하지 않는다. 최근 roster와 detail 결합에도 시간차와 노선 변경의 한계가 있다.

서울 roster의 번호 대조 목록을 제공하기 위해 모든 차량 detail을 선행 필수화하지 않는다. detail을 조회하지 않은 차량의 정류장 위치는 미확인으로 표시한다. 위치 설명 또는 확정 검증에 필요한 detail만 조회하고, 부분 조회·실패 범위를 명시한다. 검증되지 않은 coarse field 관계로 후보를 버리지 않는다. 기본 비용은 TAGO Route당 1회, 서울 roster 1회 + 실제 고유 detail 조회 수이며 실패 retry·재조회 비용은 별도다. 기존 공유 가능한 경로를 활용하되 전용 캐시·새 Polling 주기·quota 정책·인프라를 선행 결정하지 않는다.

TASK-901의 과거 pagination·필수 필드 실패·서울 미호출 기록은 소급 수정하지 않는다. 이 ADR의 최신 가용 데이터 수용은 운영상 입력 정책 결정이며, 과거 미검증 freshness·물리 차량 동일성·도착 정확성을 실측 검증된 사실로 바꾸지 않는다.
